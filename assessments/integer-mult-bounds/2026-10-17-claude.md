## Suggestions (don't affect grades)

1. **Make the handoff lifecycle machine-visible.**
   - Have `find_overlap.py` treat a handoff as taken when a reply carries a CLAIM, DONE or STOP that links it, as #3145's replies do.
   - Or prompt handoff authors to edit their block.
   - Handoffs now live in many discussions (#3145, #3156, #2976, #2319), with prose pointers in #1166. The overlap reader only sees structured blocks.
2. **State the runtime and hardware** of `make frontier1094-verify` next to it in `README.md` and the selected record. If possible, add an incremental check of the #1094 step that needs no native build, so a verifier can finish in minutes.
3. **Separate intake from scientific review in the ledger's live counts.** Response times are fast, but merges are archival (`CONTRIBUTING.md:40-42`), and 576 PRs are only "partially reviewed". A headline count of results awaiting scientific review would help donors and the hub.
4. **Add a one-paragraph plain-language problem statement near the top of `autoresearch.md`.** The probe inferred the problem from the κ framing.
5. **Fix `find_overlap.py`'s noisy output.** It returned 611 matches for one card, mostly sibling `TASK.json` files for the same card. Group them by package, or rank them by recency.
6. The repo's `discover.json`-free setup works well through the adapter. A `discover.json` with `credit` and a `.github/discover-hubs.json` consent record would let the hub retire the adapter.

## Doesn't fit the rubric

- **Review measures any first response, but here a merge is archival intake, not acceptance** (`CONTRIBUTING.md:40-42`). The project's scientific bottleneck isn't measured:
  - newer κ claims (#2979) wait as "source archives";
  - 576 PRs are "partially reviewed";
  - the frontier hasn't moved since #1094.

  Review is strong by the rubric, but the rubric could separate first response from the time to a recorded acceptance or rejection.
- **Scale.** About 3,000 PRs in ten days, about 250 open, over 2,200 research packages. The 14-day window and the "two open handoffs" probe assume far less traffic. The duplicate rate can't be measured by hand at this volume, so I used a title-similarity proxy. The spec should name a sampled method, for example a seeded sample of 50 PRs checked by hand.
- **Too few open handoffs for the probe.** The coordination probe asks for two open handoffs on one track, but this project had at most one, and it was stale. The rubric should say how to grade when the true answer is "none open".
- **Verification by inspection.** The hub's run policy (no builds, a few minutes) means a project whose check needs a native build can't reach strong. That's arguably right, but it should be stated, along with what counts as a "fixed budget".
- **The maintainer's handle.** The registry `contact` is `colkitt`, but the maintainer acts as `Mister-Meeseeks`. The registry has no field for the maintainers' GitHub handles, which the Review measurement needs.
- **The playbook's hash didn't match a cached helper.** The playbook pins a helper hash. A pre-existing `~/discover-work/discover.pyz` didn't match it; a fresh download did, and I used that.
