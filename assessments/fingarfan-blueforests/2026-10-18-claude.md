## Why this repo

The card asks whether the §3 rubric grades a replication- or conjecture-shaped project
sensibly. The donor's interests were marine biology and ecology. GitHub search (terms
`replication marine` in descriptions) gave three ecology replication repos:
`Fingarfan/BlueForests`, `lanzen/Metamon1` and `msimoes123/CrustaceaENM`. The pick was made
from the seed, not by preference: index
`sha256(seed + ":candidate") mod 3` = 0 over the sorted list.

This is a **replication package**: the authors' own code for reproducing their paper
("Assessing Ecosystem Services Provision using Bayesian Belief Network in Southern Europe
Marine Forests"; kelp at Peniche, Sines and Viana do Castelo, plus seagrass). It is not a
third-party replication project. That shape is common in ecology and economics, but it's
only one of the shapes the card has in mind (see *Rubric fit*).

## Grades

### 1. Orientation: weak

Self-run probe, about 5 minutes of reading (the repo is 10 files):

1. *Problem?* Partly answered. The README says "the code that can be used to replicate the
   results of this paper" but doesn't name the paper. Only the GitHub repo description
   names it, and nothing gives a DOI or citation.
2. *Strongest accepted result and its scope?* Missing. The results live in the paper,
   which isn't linked, and the repo has no results file or expected outputs.
3. *Where is help most useful?* Missing. Nothing is stated.
4. *How to claim, submit and get it checked?* Only "If you have any questions about the
   code, please email the authors" (`README.md`). There's no contribution path.

Two answers are missing, so it's weak.

### 2. Coordination: weak

There's no task list, no handoffs and no channel in use. Issues are enabled, but the repo
has never had an issue or PR (`gh api repos/Fingarfan/BlueForests/issues?state=all` →
0). Spread: agents would choose freely from prose, and there's barely any prose. Live
state: there's no public channel to probe.

### 3. Verification: weak

- No single record states what's accepted. The paper is implicitly the record, and it
  isn't linked.
- The check can't be run by anyone but the authors: `BN_Discretize.R:12` and
  `Simulations_Dataset.R:11` read `DATASET.xlsx`, which "can be made available upon
  request at the discretion of" a named author (`README.md`). Under §3.2 the results
  "can be accepted only by trusting their author", or after a private request.
- The declared entry point is broken as written: `run_this.R` calls
  `source('BN_Discretize_Final.R')`, but the repo's file is `BN_Discretize.R`. Found by
  inspection, not by running it.
- The setup is partly pinned. `bnlearn` is pinned to 4.9.1 (`run_this.R`), while
  `gRain`, `graph`, `Rgraphviz`, `RBGL` and `readxl` aren't. `setwd(...)` relies on
  `rstudioapi::getSourceEditorContext()`, so it only works inside RStudio. The README
  recommends at least 32 GB RAM. The pipeline's steps and intermediate files are listed
  (`*.RData`), and that part is good.

### 4. Review: unknown

There were zero contributions ever, none in the window, and no declared capacity.

### 5. Steering: weak

There are no stated priorities. The repo describes a finished paper, not ongoing work.

## Stage: assessed

There's no maintainer consent and no `LICENSE`/`LICENCE`/`COPYING` (GitHub reports
`license: null`). Even with consent and a license, Orientation is weak, so Stage 0
would be blocked.

**What blocks Stage 0** (for the maintainers, if they ever wanted it; the hub doesn't
contact them, §11.4): a license, consent, a credit policy, and a README that names and
links the paper and its headline results, with a contribution route.

## Suggestions (don't affect grades)

- Fix `source('BN_Discretize_Final.R')` → `source('BN_Discretize.R')` in `run_this.R`.
- Cite the paper (DOI) in the README, and list the figures and tables each script
  reproduces.
- Ship a small synthetic `DATASET.xlsx` with the same sheet layout (`Design_1`), so the
  pipeline can be smoke-tested without the restricted data.
- Pin the remaining R packages (for example with `renv.lock`), and replace the
  RStudio-only `setwd` with `here::here()` or a working-directory note.
- Add a license.

## Rubric fit: where §3 didn't fit this shape

1. **Finished replication packages have no "ongoing work".** Orientation Q3 ("where is
   help most useful") and Steering presume live research. For an archived package, the
   useful donated work would be *rerunning it*, and the rubric has no way to say "the
   project's work is complete; contributions are reproductions". It grades the package
   weak on Steering for not having priorities it was never meant to have. Suggestion: a
   `shape` field (or a `closed`/`archival` status) under which Steering is *n/a*, and
   Orientation Q3 reads as "what a reproduction should check".
2. **Restricted data is not the same as no check.** In ecology, field data are often
   embargoed or shared on request for legitimate reasons. §3.2 Verification puts "data
   on request, pipeline public" in the same bucket as "trust the author", so it can't
   separate this repo from one with no code. The spec could add an explicit note, or a
   sub-grade like *verifiable with restricted inputs*, with a synthetic-data smoke test
   as the route to adequate.
3. **The hardware requirement can't be expressed** (32 GB RAM here). This is the same gap
   the `applied-butterfly-mult` records found for non-M2 machines.
4. **Field coverage.** No listed project is in the life sciences. The explore playbook's
   interest-to-field step ("marine biology and ecology") matched no hub domain, and the
   draw fell back to all projects. That's a gallery and second-pilot signal, not a rubric
   gap.
5. **Shape coverage is still incomplete.** This record tests the *authors' own
   replication package* shape. A *third-party replication* (reproducing someone else's
   claim) and a *conjecture-style* project are still untested.
