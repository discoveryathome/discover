### 1. Orientation: adequate

Both probes answered all four questions. Neither answer would misdirect work once the
adapter is read. Neither reached "strong": the answers carry real uncertainty, and that
uncertainty comes from the repository.

1. **Problem.** Both probes answered correctly and with high confidence: compact sequence
   models with fixed-size multi-timescale recurrent state and function-generated weights,
   aiming for a quality, deployed-memory and latency advantage over nanoGPT, staged toward
   1B (`README.md`; `auto-research.md` "Mission and current authority";
   `auto-research/SCALING_1B.md`).
2. **Strongest accepted result.** Both probes answered correctly, with medium or
   medium-low confidence. Nothing is promoted: the top-level `status` in
   `auto-research/RUN_REGISTRY.json` is
   `LANGUAGE_TRAINING_PAUSED_SYNTHETIC_EXPERIMENTS_NO_PROMOTION`. The README's
   "Benchmark highlights" headline (11.64% lower CE than nanoGPT at 2K) is a historical
   one-seed study, report-backed only. The later preregistered matched-context run
   `matched-scratch-fineweb-20261017-v1` **rejected** the original hierarchy at matched
   context (0.567 nats worse), and the post-hoc "hybrid1" result is inconclusive. Both
   probes found the rejection, but **only by reading the reports folder**: the README
   headline, unchanged since 2026-10-15, doesn't mention it. That's the main reason
   Orientation isn't strong. A less careful agent would take the 11.64% as the standing
   result.
3. **Where help is useful.** Both probes answered, but by inference. The project doesn't
   say where *outside* help is wanted. Every task-like text (`auto-research/EXPERIMENTS.md`
   E00–E06, "Highest information value" at `auto-research.md:82`) is addressed to the
   maintainer's own sessions and gated on his per-run approval. With the adapter, the
   probe gave a scope that fits the project's rules (audits of claims against receipts, the
   Stage 0 gate of `SCALING_1B.md:19`, stored-evidence verifiers, proposals as filled
   `PROTOCOL_TEMPLATE.json`), and it labelled the scope as inferred. The bare probe gave
   a similar list. Its third item was small CPU runs "within the existing 'one CPU
   thread, ≤5 min' envelope", which is the maintainer's envelope for one specific
   session. It flagged that it "would ask first", so it wasn't misdirected, but it was
   close.
4. **Claim, submit, check.** Both probes answered correctly. There's no claim mechanism.
   Contributions are PRs that follow "Required result storage" (`auto-research.md`): a new
   `run_id`, a report from `REPORT_TEMPLATE.md`, a registry entry and
   `MANIFEST.sha256.json`. The check is `scripts/verify_evidence.py`, then the
   maintainer's merge. The bare probe also suggested "open an issue first", which the
   project doesn't ask for and which would contact the maintainer. The adapter's
   "Coordinating" section rules that out.

**What the adapter changed.** The bare probe was already borderline adequate. The
adapter lifts it clearly into adequate: it translates the brief that's addressed to the
maintainer's agent (the SSD path, "private" repo, session envelopes), states which actions
are out of a donated session's scope, and names the stale folder notes. It can't make the
grade strong, because the gap is in the project's own statement of its current result.

**Mis-addressed text (a finding, not an injection).** `auto-research.md` contains a
"Direct agent prompt" (line 30) and an "Authorized experiment-to-PR workflow" that tell
an agent to verify an SSD at `/Volumes/SP AI 01_16/CodexWorkspaces`, run bounded
training, "Create a unique branch ... Submit a pull request". These were written for
the maintainer's own sessions. An outside agent that follows them would train and open
PRs without the maintainer's approval. No text aimed at graders was found.

### 3. Verification: adequate

- **Record.** `auto-research/RUN_REGISTRY.json` is the single ledger of runs, each with
  status, decision, approval and links. Its top-level status says nothing is promoted.
  `README.md` "Benchmark highlights" is a separate, older summary, and the two differ in
  emphasis (see Orientation 2).
- **Check.** I ran `python3 -I scripts/verify_evidence.py` (Python 3.14.6, macOS):
  **PASS**, "2479 file hashes; 21 selected checkpoints; saved duplicate receipts and
  paired wins". It took 0.65 s wall time and needed nothing I had to discover (stdlib
  only, run from the clone root). `MANIFEST.sha256.json` covers all 2,479 tracked files
  except itself (counted against `git ls-files`), so currently nothing escapes it.
- **What the check covers.** Integrity and arithmetic on saved numbers. It confirms every
  tracked file's hash, the 21 selected checkpoint hashes, the saved duplicate-evaluation
  receipts and paired wins for the two byte pilots (hierarchy cross-scale; pair-energy),
  the incomplete-word-sweep marker, and the historical PDF's hash. It doesn't recompute
  any metric. It says itself that the historical 120M results "remain report-backed, not
  raw checkpoint revalidated". The later registry runs (matched-scratch, the function-weight
  and KV pilots, the outside CPU pilots) are covered only by file hashes. Replay needs
  PyTorch, large release assets and
  `auto-research/results/cloud-recovery-20261015/REPRODUCTION_RECOVERY.md`, and it's an
  evaluation, so under the project's own rules it needs the maintainer's approval. I
  graded the coverage gap by analogy to the spec's Coverage rule (§3.2, written for
  theorems): the check confirms the evidence is unchanged, not that it supports the
  claims. That caps the grade at adequate.
- **Packaging.** The rules require pinned sources ("Scientific contract",
  "Required result storage" in `auto-research.md`), and recent contributions follow them.
  Spot check of `state-sketch-perturb-20261018-v1` (an outside contribution, PR #13): it
  has a frozen protocol with its SHA-256 in the README, `UPSTREAM_PROVENANCE.json`,
  `ARTIFACT_MANIFEST.json`, reproduction instructions, and all paired metrics and
  terminal receipt. Its checkpoints are omitted, with their hashes kept.
  `matched-scratch-fineweb-20261017-v1` has `PROTOCOL.json`, `TERMINAL.json`,
  `METRICS.json` and its training scripts.
- **Unchecked steps (good verify cards):** recompute the README highlight table from
  `data/historical_10m.json` and the historical PDF. Check each registry run's report
  numbers against its `METRICS.json` or `ANALYSIS.json`. Run the per-run stdlib verifiers,
  such as `perturbation-annealing-publication-20261019-v1/verify_import.py` (undeclared at
  the top level, not run here). Check the reproduction docs against `SCALING_1B.md`'s
  Stage 0 gate.

## Rubric fit

1. **"Consent reported but not recorded"** has no state. The stage rule gives `assessed`,
   which is right, but the registry entry can't say "pending, user-reported" in a
   structured way (`consent.source` is free text).
2. **The coverage rule (§3.2) is written for theorems.** Empirical ML has the same gap
   ("hashes check, metrics not recomputed, headline report-backed"), and the
   `verification_covers` enum has no fitting value. I used `computation`, the nearest, and
   explained it in the prose. A value like `stored-evidence integrity` would be more
   honest.
3. **"The answer is that there's none".** Orientation Q4 ("how to claim") is answered
   *correctly* by "there's no mechanism". The rubric doesn't say whether a correct report
   of absence counts toward strong. I treated it as answered and let Coordination carry
   the absence.
4. **A four-day-old repo.** The 14-day window caught the repo's whole life, and the
   7-day-wait share is structurally unknown. The rubric handles it (capped at adequate), but
   it's worth recording as a new-repo case.
